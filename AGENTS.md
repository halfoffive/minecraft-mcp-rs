# minecraft-mcp-rs — MCP server that controls a Minecraft bot

An MCP (Model Context Protocol) server backed by an actual Minecraft bot via the azalea library. Exposes bot capabilities (movement, block manipulation, inventory, combat, chat) as MCP tools consumable by LLM clients. Ships with an egui desktop UI for status and settings.

- **Stack:** Rust nightly (edition 2024; azalea 0.15.1's build script requires nightly), azalea 0.15.1 (Minecraft 1.21.11 bot), rmcp (MCP server), egui/eframe 0.34.3 (desktop UI), tokio 1.50 (async runtime), bevy_ecs 0.18 (azalea's ECS), schemars 1.0 (MCP JSON schemas), proptest (property testing)
- **Entry point:** `src/main.rs` — creates shared state + channel, spawns MCP server on background thread + egui on main thread. Bot connection is spawned on a dedicated OS thread from the UI (azalea's `ClientBuilder::start` internally creates a `LocalSet` which is `!Send`, preventing `tokio::spawn` on a multi-threaded runtime).
- **Library crate root:** `src/lib.rs`

## Architecture

Layered: **types → logic → state → bot → mcp → ui**, all in one crate.

```
src/
  types.rs            — Shared data types (BlockPos, BotCommand, WorldSnapshot, etc.)
  error.rs            — BotError enum (actionable error variants for AI agents);
                        re-exports BlockPos/ToolType/MaterialTier from types.rs
  config.rs           — AppConfig (UI settings) + RunStats (atomic counters)
  state.rs            — SharedState (thread-safe hub: ArcSwap for snapshot, RwLock for config,
                        AtomicBool for online/connecting/disconnect flags)
  block_data.rs       — Block/tool/material tables, best-tool selection
  mining_calc.rs      — Mining time formulas (the single canonical calculate_mine_time)
  command_validate.rs — Coordinate validation and command pre-checks
  snapshot.rs         — World snapshot data structures and chunk summaries
  tool_select.rs      — Best-tool selection logic
  utils.rs            — Common utility helpers (e.g. `to_snake_case`)
  compound_ops.rs     — Compound operations (e.g. mine-and-collect pipeline)
  channel.rs          — Cross-thread BotCommand channel (tokio mpsc + oneshot);
                        ReceiverSlot + ReceiverLease for executor lifecycle
  logging.rs          — tracing-subscriber setup (stderr only; stdout = MCP transport)
  bot/                — Minecraft bot lifecycle
    mod.rs            — Re-exports
    connection.rs     — ConnectionManager (connect, reconnect with backoff, disconnect)
    events.rs         — azalea event handlers (player position, chunk loads, chat)
    commands.rs       — BotCommand → azalea action execution
    ops.rs            — Higher-level bot operations (move, mine, place, etc.)
    snapshot_updater.rs — Periodically snapshots world state into SharedState
  mcp/                — MCP server
    server.rs         — McpBotServer (rmcp ServerHandler), stdio or HTTP transport
    tools_*.rs        — Tool definitions organized by domain: query, movement, block,
                        item, container, combat, chat, plus unified `act`
    render.rs         — Top-down PNG world rendering for `get_world_view`
  ui/                 — Desktop UI
    app.rs            — egui app shell
    fonts.rs          — CJK system font auto-detection + injection into egui FontDefinitions
    i18n/             — UI internationalization (functional, one file per language)
      mod.rs          — Language enum, TextKey enum, thread-safe current()/set()/tr()
      en.rs           — English lookup table
      zh_cn.rs        — Simplified Chinese lookup table
    settings.rs       — Settings panel (includes MCP transport / port / token / language)
    status.rs         — Status panel with live stats
    mcp_config.rs     — Copyable, live-generated MCP client JSON config
tests/
  integration.rs      — Mock-based end-to-end tests (no real MC server)
  proptest.rs         — Property-based tests for block_data, command_validate
```

## Conventions

- **Doc comments (`//!`)** on every module, doc comments (`///`) on every public type and function.
- **Section separators:** `// ═══`, `// ----`, or `// ≡≡≡` lines between logical sections within a file.
- **Error handling:** `BotError` (thiserror) for all bot/MCP errors; `anyhow` for top-level main errors; `eyre` available but rarely used.
- **Thread safety:** `Arc<SharedState>` shared across threads; `ArcSwap` for lock-free snapshot reads; `RwLock` for config/stats; `AtomicBool` for online flag; `Mutex` for container handle and chat messages.
- **Testing:** Unit tests in `#[cfg(test)] mod tests { .. }` at bottom of each source file; integration tests in `tests/`; property tests with `proptest` crate.
- **Logging:** `tracing` crate macros only; all output to stderr (`stdout` reserved for MCP JSON-RPC transport). Enabled via `init_logging()` called once at startup.
- **Naming:** Types PascalCase, enums PascalCase, functions/methods snake_case, module file names snake_case.
- **MCP tools:** Each tool module (tools_*.rs) exposes a builder function; tool parameters annotated with `#[derive(schemars::JsonSchema)]`.
- **Formatting:** No `.rustfmt.toml` — uses default `rustfmt`.

- **Settings panel:** Uses `EditConfig` local edit buffers (in `app.rs`); fields rendered via `TextEdit::singleline`/`DragValue`. Edits applied to `SharedState` only on Connect. The `sender` parameter was removed from `settings_panel` — the UI doesn't send commands directly.
- **MCP Config panel:** Renders a copyable JSON config (with the executable's absolute path resolved at runtime) for MCP clients like Claude Desktop / Cursor. Uses egui 0.34.3's clipboard API; schemars 1.0 `Schema` (via `schema_for!`) drives any schema rendering.
- **Bot connection:** Spawned on dedicated OS thread (not `tokio::spawn`) because `ConnectionManager::connect()` contains `LocalSet` which is `!Send`. The thread's `JoinHandle` is held by `MinecraftApp` and joined on `Drop` for clean exit. `Drop::join` has a 3-second timeout so closing the window never hangs.
- **Command executor:** Wired into `Event::Spawn` via `spawn_local`. The command receiver is stored in a `ReceiverSlot` (`Arc<Mutex<Option<BotCommandReceiver>>>`) and leased out via `ReceiverLease` on Spawn; when the executor is aborted on `Event::Disconnect`, the lease drops and returns the receiver to the slot for the next reconnect. `Event::Disconnect` also writes `AppExit::Success` to the ECS (`bot.ecs.lock().write_message(AppExit::Success)`) so `ClientBuilder::start` returns and the connect loop can retry (azalea 0.15.1 removed `Client::exit()`).
- **Connect/Disconnect:** `SharedState` has `bot_connecting` (AtomicBool) and `disconnect_requested` (AtomicBool) flags. `try_begin_connecting` guards against double-spawn. `request_disconnect` tells the reconnect loop to stop; the Disconnect button sets it. `clear_connecting` is called when the connect loop exits. A `CancellationToken` (from `tokio-util`) is stored in `SharedState` and cancelled on disconnect so the reconnect backoff sleep returns immediately instead of blocking shutdown. **`ClientBuilder::start()` is wrapped in `tokio::select!` with `cancel_token.cancelled()`** so a disconnect request during the TCP connect attempt (~5 s) aborts immediately via `break` instead of waiting for `start()` to return (variable name `start_cancel` to avoid shadowing the later `cancel_token` locals used for backoff/retry sleeps).
- **`windows_subsystem` conditional compilation:** `src/main.rs` carries `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]` after the crate-level doc comments. Debug builds (`cargo run`) retain the console window for diagnostics; release builds (`cargo run --release`) hide it. This attribute is Windows-only and ignored on other platforms.
- **Connection errors:** `SharedState::last_error` (behind a `Mutex<Option<String>>`) surfaces the most recent connection failure to the UI; the Status panel renders it in red. Connection failures are fail-fast — the reconnect loop stops retrying so the user sees the error and can manually retry, rather than looping infinitely.
- **Type unification:** `error.rs` re-exports `BlockPos`, `ToolType`, `MaterialTier` from `types.rs` — no duplicate definitions. `ToolType` has 7 variants (Pickaxe, Axe, Shovel, Hoe, Sword, Shears, Hand). No `to_error_*` bridge helpers needed.
- **Snapshot building:** `handle_tick` delegates to `SnapshotUpdater::update_from_tick` — the inline `build_and_update_snapshot` and helper functions were deleted from `events.rs` to avoid duplication with `snapshot_updater.rs`.
- **Mutex poisoning recovery**: Extended from `SharedState` to all shared mutexes (including `channel.rs` command receiver slot, `bot/events.rs` executor handle, and `logging.rs` test helpers). All use `.unwrap_or_else(|e| e.into_inner())` to prevent cascade crashes.
- **`SharedState::modify_snapshot` 约定:** 事件 handler 更新快照部分字段（entities / self_player.health 等）**必须**用 `SharedState::modify_snapshot<F: FnMut(&mut WorldSnapshot)>(&self, f: F)`，基于 `ArcSwap::rcu` 原子读-改-写。闭包签名为 `FnMut(&mut WorldSnapshot)`（**不是 `FnOnce`**，因为 `rcu` 在并发更新下可能重试）。**禁止**再用 `read_snapshot().clone()` + `update_snapshot()` 模式 —— 该模式会丢更新（`SnapshotUpdater` 在 await 点交错时会把字段原样写回，抹掉事件 handler 的修改）。`handle_death` / `add_player_to_snapshot` / `handle_remove_player` / `handle_update_player` 已迁移到此 API。
- **`command_sender` 注入链路约定:** `Act::Mine` 需要委托 `CompoundOpExecutor` 完整执行（选工具→走过去→挖掘→验证）。由于 azalea ECS 通过 `BotState::default()` 构造 `BotState`，无法直接传参，采用与 `INJECTED_SHARED_STATE` / `INJECTED_COMMAND_RECEIVER` 同模式的 `Mutex<Option<T>>` 注入：`ConnectionManager::connect(command_receiver, egui_ctx, command_sender)` 在重连 `loop` **内部**（C-2 修复）每次迭代 `events::INJECTED_COMMAND_SENDER.set(Some(command_sender.clone()))`；`BotState::default` 读取该 static 得到 `command_sender: Option<BotCommandSender>`；`handle_spawn` 在 `async move` 闭包**外**提前 `let command_sender = state.command_sender.clone();`（避免 E0521 borrowed data escapes）传入 `CommandExecutor::new_for_lease(client, shared_state, command_sender)`；`CommandExecutor::sender: Option<BotCommandSender>` 标注 `#[allow(dead_code)]` —— **C-1 修复后 `handle_act` 不再使用 `sender` 字段**，仅保留以免改动 `connect` 调用链；`handle_act(Mine)` 现在直接把 `self`（`&CommandExecutor`）传给 `CompoundOpExecutor::execute_mine_block(self, pos, true)`，`CompoundOpExecutor` 已重构为单元结构 + 关联函数（`fn execute_mine_block<B>(executor: &CommandExecutor<B>, pos, verify) -> ...`），通过 `executor.dispatch(cmd)` 直接派发子命令而非走 `BotCommandSender` 通道（旧实现会在单消费者执行器循环上自死锁）。递归调用链 `dispatch → handle_act → execute_mine_block → dispatch` 通过在 `handle_act` 内用 `Box::pin(execute_mine_block(...))` 包装解决 E0733（async fn 递归）。`INJECTED_COMMAND_SENDER` 仍按 C-2 在 `connection.rs::connect` 的 `loop` 内每轮重新 set（不再被 `CompoundOpExecutor` 消费，保留供未来用途）。`MinecraftApp` 持有 `sender: BotCommandSender` 字段（来自 `main.rs` 的 `sender_for_egui`），`connect_bot` clone 一份传入 `manager.connect(...)`。
- **`shutdown_token` 生命周期约定:** `SharedState` 持有 `shutdown_token: Mutex<CancellationToken>`（来自 `tokio-util`，与 `cancel_token` 字段独立 —— `cancel_token` 用于打断 reconnect backoff sleep，`shutdown_token` 用于 MCP graceful shutdown，两者生命周期独立）。通过 `shutdown_token() -> CancellationToken` 暴露（克隆返回）、`trigger_shutdown()` 触发。`MinecraftApp::drop` 调用 `trigger_shutdown()`；`serve_http` 在 `app` 构造前 `let shutdown_token = state.shutdown_token();`（因为 `.with_state(state)` 消费 state），再用 `axum::serve(listener, app).with_graceful_shutdown(async move { shutdown_token.cancelled().await; })`（**必须用 `async move` 包装** —— `CancellationToken::cancelled()` 返回的 future 借用 token，非 `'static`，不满足 `with_graceful_shutdown` 的 `Send + 'static` 约束）；`serve_stdio` 在 `McpBotServer::new(state, sender)` 前 `let shutdown_token = state.shutdown_token();`，再用 `tokio::select!` 并联 `running.waiting()` 与 `shutdown_token.cancelled()`，shutdown 触发时立即返回不等 stdin EOF。MCP 线程 `JoinHandle` 现存于 `MinecraftApp`，drop 时 join（3 秒超时，与 bot 线程一致）。
- **`tick_abort_handles` 约定:** `BotState` 新增字段 `tick_abort_handles: Arc<Mutex<Vec<AbortHandle>>>`，追踪 `handle_tick` 中 `spawn_local` 的 tick 任务 `AbortHandle`。`handle_disconnect` 时 abort 全部并清空，防止 ECS 拆除后 tick 任务调用 `bot.component()` / `bot.world()` 触发 panic 或写入陈旧快照。模式与 `executor_handle` 一致（`take()` + abort）。

- **Injection globals are `Mutex<Option<T>>`:** the four values injected into `BotState::default` (`INJECTED_SHARED_STATE`, `INJECTED_COMMAND_RECEIVER`, `INJECTED_EGUI_CTX`, `INJECTED_COMMAND_SENDER`) live in `Mutex<Option<_>>` rather than `OnceLock` so they can be reset on disconnect / between tests. **C-2 修复后：`ConnectionManager::connect` 在重连 `loop` 内部每次迭代都重新 `set` 这四个全局**（不再是在进入 azalea 循环前只 set 一次），因为 `handle_disconnect` 会把它们全部清空回 `None`，旧实现的"循环外只 set 一次"导致重连时所有注入字段为 `None`，bot 在 `Spawn` 时拿不到 `shared_state` / `command_receiver` / `egui_ctx` / `command_sender`。`command_sender` 每轮迭代 `.clone()` 一份。`handle_disconnect` 仍负责清空全部回 `None`。这保证重连和单元测试都能看到新鲜的注入状态。 **`ReceiverLease::take` 失败需 yield 重试（≤100ms）：** 在 `handle_spawn` 中，当 `Event::Spawn` 比 `ReceiverSlot` 的清空（`handle_disconnect` → `executor_handle.take()`）早到（例如上一连接刚断开、新连接立刻建立的快速重连场景），首次 `slot.lock().unwrap_or_else(...).take()` 可能返回 `None`。正确做法是循环 `tokio::task::yield_now().await` + `tokio::time::sleep(Duration::from_millis(100))` 重试 100ms（最多 ~10 次），如果仍然 `None` 则进入"无执行器" warn 路径（log + 继续接收 azalea 事件但不处理 MCP 命令）。禁止立刻 return/spawn 失败 — 那样 MCP 工具会在重连期间一直报"bot offline"。回归测试：`test_receiver_lease_take_retries_during_reconnect` 在 `src/bot/events.rs::tests` 中并发触发"disconnect → spawn"序列，断言重试期间 lease 成功拿到 receiver。
- **`BotCommand::UseItemWithSlot`:** use this single command when an MCP tool needs to "switch to slot X and then use the item". The switch and the use happen inside the same executor critical section, so concurrent commands cannot interleave a different `SwitchHotbarSlot` between them. `tools_item::handle_use_item` sends `UseItemWithSlot(slot)` when `item_slot` is provided, otherwise falls back to parameterless `UseItem`.
- **Nearby queries are parameterised:** `get_nearby_blocks` and `get_nearby_entities` accept a `radius` argument (and `get_nearby_blocks` also accepts an optional `filter_type` substring). The tool input structs derive `Deserialize` and `rmcp::schemars::JsonSchema` and are wired through `Parameters<T>` in `server.rs`; the handlers no longer hardcode a radius.
- **MCP tool schemas use derive:** input structs in `tools_*.rs` use `#[derive(Deserialize, rmcp::schemars::JsonSchema)]`. Hand-written `impl JsonSchema` is reserved for cases where the derive truly cannot express the schema; adding it just to work around an old `schemars`/`rmcp` conflict is not acceptable because it drifts silently when fields change.
- **Tool schema range annotations:** bounded numeric MCP parameters (e.g. `WalkDirectionInput.distance`, `SwitchHotbarSlotInput.slot`) carry `#[schemars(range(min = ..., max = ...))]` so clients see the limits in the generated JSON Schema.
- **Common `to_snake_case` helper:** `src/utils.rs::to_snake_case` is the single implementation for converting azalea registry variant names (e.g. `IronPickaxe`) into snake_case item ids. Both the command executor and snapshot updater import it from `crate::utils`; do not re-implement it locally.
- **Deprecated `block_data::find_best_tool_in_inventory`:** this function is `#[deprecated(note = "use tool_select::find_tool_in_inventory instead")]` and delegates to `tool_select::find_tool_in_inventory`. New code and tests should call the `tool_select` version directly; the deprecated re-export remains only for backward compatibility.
- **Block-update packets (M-2):** `Event::Packet(Arc<ClientboundGamePacket>)` is the catch-all for game packets — azalea 0.15.1 has no dedicated `BlockUpdate` event variant. `handle_event` matches `Event::Packet(packet)` and dispatches to `handle_packet_block_updates(state, &packet)`, which pattern-matches `ClientboundGamePacket::BlockUpdate(data)` → `dirty_tracker.mark_block_dirty(data.pos)` and `ClientboundGamePacket::SectionBlocksUpdate(data)` → iterates `data.states` and computes each block's world `BlockPos` via `data.section_pos + entry.pos` (azalea-core provides `impl Add<ChunkSectionBlockPos> for ChunkSectionPos`). All other packet variants are ignored. The tracker lock uses `.unwrap_or_else(|e| e.into_inner())` for poisoning recovery. Without this handler, single-block updates from the server (block break/place by other players, piston extension, water flow) would never mark the snapshot dirty and the bot would see stale world state.
- **`find_standable_neighbor` (M-4):** `execute_mine_block` must NOT use the target block's own position as the `MoveTo` destination — the bot would path into the block and get stuck. Instead, call `compound_ops::find_standable_neighbor(&snapshot, target_pos)` which scans the 8 horizontal neighbours × 3 Y levels (priority: same Y → y+1 → y-1) and returns the first air block with a solid block below it. Block lookups go through `WorldSnapshot::block_index` (M-12) — O(1) per check, not O(N) linear scan. If no standable neighbour exists, the state machine transitions to `Failed(PathfindingFailed { move_target: target_pos })` rather than attempting an unreachable path.
- **`WorldSnapshot::block_index` (M-12):** `WorldSnapshot` carries a `block_index: HashMap<BlockPos, usize>` (`#[serde(skip)]` — derived from `blocks`, not part of the MCP JSON contract). `SnapshotBuilder::build` constructs it via `blocks.iter().enumerate().map(|(i, b)| (b.position, i)).collect()`. Code that needs to look up a block by position MUST use `snapshot.block_index.get(&pos)` → `&snapshot.blocks[idx]` rather than `snapshot.blocks.iter().find(|b| b.position == pos)` — the index is O(1), the linear scan is O(n) and was a hotspot for large snapshots. New `WorldSnapshot` literals must add `..Default::default()` (or `block_index: HashMap::new()`) since the field is non-optional. **`execute_mine_block` MUST go through `block_index` in both Step 2 (look up the target block's `block_type` to choose a tool) and Step 10 (verify the block was actually broken by re-reading via `block_index.get(&pos).is_none()`).** Linear `Vec::iter().find()` lookups inside the state machine are forbidden — they make the hot path O(n) per tick and have repeatedly regressed this code path. Regression test: `test_mine_block_uses_block_index` with a 5000-block snapshot must complete in < 1 ms.
- **`McpServerStatus` (M-13):** `SharedState` exposes `mcp_server_status: Mutex<McpServerStatus>` with `set_mcp_server_status()` / `get_mcp_server_status()`. `serve_http` calls `set_mcp_server_status(Running(addr))` after a successful bind, `Failed(msg)` on bind failure (also calls `set_last_error`), and `Stopped` when the server exits. `serve_stdio` calls `Stdio` at start and `Stopped` at end. The Status panel renders the current value so users can see whether the MCP server is up, where it's listening, or why it failed — without checking the terminal.
- **First-connect retry (M-9):** `ConnectionManager::connect` retries the first connection (`!was_online`) up to `MAX_FIRST_CONNECT_RETRIES = 3` times with a 2-second interval before falling through to fail-fast. This handles transient DNS / network blips on startup without entering an infinite retry loop. The retry sleep races `cancel_token()` so a disconnect request aborts immediately. Subsequent reconnects (after the bot was online) remain fail-fast — only the very first connection gets the retry window.
- **HTTP TLS warning (M-8):** when `mcp_transport == McpTransport::Http` AND `mcp_address` is not in `["127.0.0.1", "::1", "localhost"]`, both the Settings panel (below the Bind Address input) and the MCP Config panel render a red warning: "⚠ No TLS — use trusted network or reverse proxy". This reminds users that MCP HTTP transport has no encryption and should be put behind a TLS-terminating reverse proxy (e.g. nginx) when binding to a non-loopback interface.
- **`Offline` vs `CommandTimeout` semantics (S-4):** `BotCommandSender::send_command` distinguishes two failure modes: (1) `BotError::Offline("bot command channel closed")` — the receiver was never there or has been dropped; (2) `BotError::Offline("bot command responder dropped without reply")` — the receiver accepted the command but dropped the oneshot responder without replying (executor aborted/panicked mid-command). The third mode, `BotError::CommandTimeout`, is reserved for the genuine "responder is alive but slow" case (the `tokio::time::timeout` branch). Previously the responder-dropped case was incorrectly classified as `CommandTimeout`, hiding the fact that the bot was gone rather than merely slow. Tests asserting "responder dropped → Offline" live in both `src/channel.rs::tests::test_offline_when_responder_dropped` and `tests/integration.rs::test_offline_returned_when_responder_dropped*`. **MCP error mapping (Offline → -32000 SERVICE_UNAVAILABLE):** when `BotError::Offline(_)` is converted to MCP `ErrorData` (via `From<BotError> for ErrorData` in `src/error.rs` AND the `IntoCallToolResult` impl), the resulting JSON-RPC code MUST be `-32000` (JSON-RPC "server error" range, semantically `SERVICE_UNAVAILABLE`) — NOT the generic `-32603 InternalError` it was previously mis-mapped to. The error data field carries `serde_json::json!({"reason": "bot_disconnected"})` so MCP clients can distinguish "bot is gone, retry later" from "input is invalid" (`-32602`) and from "internal server error" (`-32603`). Both `test_into_mcp_error_offline_uses_service_unavailable` (the new assertion) and the updated `test_into_mcp_error_offline` (asserting the `reason` payload) live in `src/error.rs::tests`.
- **Lazy command logging (S-5):** `send_command` clones `cmd` into `cmd_for_log` and uses `tracing`'s `?cmd_for_log` lazy formatting (`trace!(command = ?cmd_for_log, ...)`) so the `Debug` formatting is only paid when the log level is enabled. The previous `format!("{:?}", cmd)` ran unconditionally on every call. The `format!` is now only in the `CommandTimeout` error path (which needs an owned `String` for the error variant).
- **Default log filter (S-7):** `logging.rs::init_logging` uses `EnvFilter::try_from_default_env().unwrap_or_else(|_| EnvFilter::new("minecraft_mcp_rs=debug,azalea=warn"))`. The default `minecraft_mcp_rs=debug` makes bot internals visible without setting `RUST_LOG`, while `azalea=warn` suppresses azalea's chatty info logs. Override with `RUST_LOG=info` or any other filter as usual.
- **Harvest Level (H-1):** vanilla Minecraft's tool tier system is enforced. `block_data::HARVEST_LEVEL: HashMap<&str, u8>` maps a block's required harvest tier: `Wood=0, Stone=1, Iron=2, Diamond=3, Netherite=4` (lower numbers are weaker). `tool_select::find_tool_in_inventory` now takes a `required_harvest_level: u8` parameter; any tool whose own `ToolMaterialTier < required` is rejected as `None` (NOT optimistically selected). The table covers at minimum `Stone` (→Iron, 2), `Cobblestone` (→Iron, 2), `IronOre`/`DeepslateIronOre` (→Stone, 1), `DiamondOre`/`DeepslateDiamondOre` (→Iron, 2 — needs iron pick to harvest the ore block, then drops diamond; some sources say stone is enough to break but no drops, iron guarantees the drop), `Obsidian` (→Diamond, 3), `AncientDebris` (→Diamond, 3), and `NetheriteBlock` (→Netherite, 4). When `find_tool_in_inventory` returns `None`, the caller MUST surface a `BotError::ToolNotFound { alternatives: [<next-tier tool name>] }` (e.g. "use an Iron Pickaxe to mine Diamond Ore") so the LLM client can tell the user to upgrade. **木镐不能挖钻石矿** (wood pickaxe cannot mine diamond ore — the best tool is silently downgraded, which loses resources and the player does not know why). Regression tests: `test_harvest_level_wood_cant_mine_diamond` (asserts `None` + `alternatives: ["IronPickaxe"]`) and `test_harvest_level_diamond_mine_diamond_ore` (asserts `Some(DiamondPickaxe)`). `mining_calc::calculate_mine_time` is unaffected — harvest level is a gate, not a speed multiplier.
- **`ClearGuard` for `bot_connecting` (R-1):** `src/ui/app.rs` defines `ClearGuard<'a>(&'a SharedState)` whose `Drop` calls `state.clear_connecting()`. The bot connection thread wraps its body with `let _clear_guard = ClearGuard(&state);` as the first statement after `spawn`. This RAII guard ensures that **even if the thread panics** (unwinding calls `Drop`), the `bot_connecting` flag is cleared. Without this, a panic in `Runtime::new()` or any other early failure before the explicit `state.clear_connecting()` at the bottom of the thread would leave the flag permanently `true`, blocking all subsequent Connect attempts. The guard is safe during unwinding because it only touches an `AtomicBool`.
- **`MinecraftApp::last_language` (R-2):** `MinecraftApp` caches `last_language: Language` to deduplicate per-frame `read_config` acquisitions for language synchronisation. The `ui()` method compares `self.last_language` against `self.state.read_config().language` and only calls `i18n::set()` on mismatch. This replaces a per-frame `RwLock::read()` that fired unconditionally even when the language hadn't changed.
- **CJK fonts now appended (R-3):** the system CJK font is *appended* (not prepended) to `egui::FontFamily::Proportional`, so Latin glyphs consistently use the primary font (Ubuntu-Light) and non-Latin glyphs fall through to the CJK font as a last resort. egui 0.34 searches all fonts in the family list, so appending is sufficient for correct CJK rendering.
- **MCP tool radius runtime enforcement (R-4):** `get_nearby_blocks` and `get_nearby_entities` in `tools_query.rs` reject `radius` outside `1..=100` with `BotError::InvalidParams` before dispatching. This matches the `#[schemars(range(min = 1, max = 100))]` JSON Schema contract. Previously, a malicious client could pass `radius=u32::MAX` and trigger pathological O(n) scans or integer-overflow-based incorrect results.
- **`clamp_to_i32` for all u32→i32 conversions (R-5):** `command_validate::clamp_to_i32` clamps a `u32` to `i32::MAX` rather than silently truncating via `as i32` (which wraps to negative for values > `i32::MAX`). All new code that converts `u32` to `i32` must use this helper or `i32::try_from`; a bare `as i32` is forbidden. `handle_walk_direction` additionally uses `saturating_add`/`saturating_mul` for coordinate arithmetic.
- **Container tool validation order (R-6):** `handle_take_from_container` and `handle_put_into_container` validate `count == 0` *before* the `check_container_open` / `is_online` gate, so a malformed parameter always yields `InvalidParams` rather than a misleading state-dependent error. This matches the convention in `tools_item.rs`.
- **`handle_collect_items` naming (R-7):** the local variable and JSON field are named `visited` (not `collected`) because `goto` success only guarantees the bot *reached* the item's position — the server may not have processed the pickup. The result message reads "Visited N item drop location(s); auto-pickup expected on proximity".
- **`handle_place_block` result message (R-8):** `"slot:N"` internal prefixes are stripped from the result message via `block_type.strip_prefix("slot:").unwrap_or(&block_type)` so the LLM sees a clean block type name rather than an opaque hotbar index.
- **`equip_tool` material preference wiring:** `EquipToolInput.material_preference` is now honoured (previously it was echoed into the response JSON but never affected tool selection). `tools_item::parse_material_tier` maps the string (case-insensitive; `wooden`/`golden` aliases accepted) to a `MaterialTier`; an unknown value returns `InvalidParams`. When present, the MCP handler sends the new `BotCommand::EquipToolWithMaterial(ToolType, MaterialTier)` instead of `EquipTool(ToolType)`; both route to `handle_equip_tool(tool, Option<MaterialTier>)`, which converts the tier to a minimum harvest level via `block_data::harvest_level_of` and passes it to `tool_select::find_tool_in_inventory`. Semantics are **minimum tier** (request Diamond → accept diamond/netherite, reject lower); requesting a tier above every matching tool yields `ToolNotFound`. Note `Gold` shares `Stone`'s harvest level (1), so a gold preference behaves like a stone preference. The plain `EquipTool` variant (used by `CompoundOpExecutor` mining) is unchanged, so its existing call sites did not move — only the four exhaustive `BotCommand` matches (dispatch in `bot/commands.rs`, `validate_command`, and the `require_all_variants`/`count_variants` test guards) gained the new arm.
- **Centralized command validation (dispatch gate):** `CommandExecutor::dispatch` calls `crate::command_validate::validate_command(&cmd)?` as its first statement (before the online check) so every command — including those generated internally by `CompoundOpExecutor` — is bounds-checked in one place. Previously `validate_command` was fully implemented and unit-tested but **never called in production**, so MCP handlers that omitted upper-bound checks (container `slot` > 53 / `count` > 64, `walk_direction` distance > 1000) let out-of-range values reach azalea. Container `count` is now also capped at 64 in `validate_command` to match the schema. Consequence: `DropItem(slot, 0)` is now rejected as `InvalidParams` at the gate (consistent with the MCP layer, which already rejected `count == 0` — see `test_drop_item_count_zero_rejected_at_mcp_layer`); the executor's `handle_drop_item` count==0 noop branch is kept as defensive-only and is no longer reachable via dispatch. Regression tests: `test_dispatch_rejects_container_slot_over_max`, `test_dispatch_rejects_container_count_over_max`, `test_dispatch_rejects_walk_distance_over_max` in `bot/commands.rs::tests`.
- **`INJECTION_READY` removed:** the `AtomicBool` guard flag in `bot/events.rs` was set on connect (`connection.rs`) and cleared on disconnect but never `load()`ed — `BotState::default` never consulted it (each injected static already has an independent fallback), so its doc comment was false. It and the now-unused `AtomicBool` import were deleted. The four injected globals remain `Mutex<Option<T>>` reset per-connection as before.
- **`find_obstacle_block` interpolation (SmartMove):** the informational obstacle scan in `bot/commands.rs` interpolates both axes proportionally (`current + total_d * i / steps`) along the true `current → target` line, instead of the previous `signum()`-based 45° diagonal that overshot the shorter axis and skipped intermediate cells. This only affects the diagnostic `obstacle` field returned by SmartMove, not pathfinding. Regression test: `test_find_obstacle_block_interpolates_line`.
- **`SelfPlayer::position_precise` and `yaw` (W-1):** `SelfPlayer` in `types.rs` carries two `#[serde(skip)]` fields — `position_precise: Option<[f64; 3]>` (sub-block-precision player position, populated by `SnapshotUpdater` from `azalea::entity::Position`) and `yaw: Option<f32>` (horizontal look direction, populated from `azalea::entity::LookDirection::y_rot()`). The top-down renderer (`render_topdown_enhanced`) uses `position_precise` for sub-pixel centre placement (eliminating the up-to-1-block truncation bias) and `yaw` for drawing a heading arrow at the player's pixel. Both are `#[serde(skip)]` so the existing JSON contract for `SelfPlayer` is unchanged — they are derived-internal fields that are `None` when the bot is offline or in test defaults.
- **World view cache (W-2):** `SharedState` has a `last_world_view: Mutex<Option<WorldViewCache>>` for caching the most recent `get_world_view` render. The cache key is `(snapshot_timestamp, radius, scale)` — a cache hit returns the same PNG + annotation without invoking `render_topdown_enhanced`. `get_world_view_cache()` / `set_world_view_cache()` / `clear_world_view_cache()` are the accessors. The UI preview panel reads from this cache; the MCP `get_world_view` tool writes to it on cache miss. Cache is single-entry (overwritten on each fresh render), keeping memory bounded.
- **Section-level chunk scanning (W-3):** `build_snapshot_inner` in `snapshot_updater.rs` now scans dirty chunks section by section (16×16×16 per section, 24 sections per chunk) instead of the previous flat 3× for loop. Before scanning each section, the chunk's `sections[].block_count` is read: if it is `0` (entirely air), the section's 4096 `get_block_state` calls are skipped. For typical surface chunks this skips ~23/24 sections, reducing the per-chunk scan from 98304 calls to ~4096 (only the surface section). The chunk read lock is held briefly to build `sections_to_scan: Vec<usize>`, then released before the per-block scan (which acquires its own lock through `world_guard.chunks.get(&chunk_pos)`).
- **`get_world_view` multi-content response (W-4):** the MCP `get_world_view` tool returns `Vec<rmcp::model::Content>` (`[image, text]`) instead of a single `Content::Image`. The text annotation is a JSON object with `center`, `radius`, `scale`, `yaw`, `snapshot_timestamp`, `image_size`, `block_count`, `entity_count`. This required an `impl IntoContents for Vec<Content>` in `patches/rmcp/src/model/content.rs` so the `#[tool]` macro accepts `Vec<Content>` return types. Scale is clamped to `[1,2,4,8]` with a fallback to 1 for invalid values.

The panel is registered in `lib.rs` and rendered as a collapsing section after the Status panel. i18n keys `Preview`, `WorldView`, `Refresh`, `WorldViewPlaceholder` have been added to `en.rs` and `zh_cn.rs`.

The supervisor polls `is_finished()` rather than blocking on `join()`, and on shutdown aborts the bot's in-flight connect attempt via `request_disconnect()` (else a dead server keeps the process alive through azalea's TCP retries).

- **Error-code table (S-12):** every `BotError` variant maps to a distinct JSON-RPC code + structured `data` (`reason`, `retryable`, variant fields). - **npm layout (S-13):** `npm/` holds the main package `minecraft-mcp-rs` (UNscoped — bin shim `bin/minecraft-mcp-rs.js`, `optionalDependencies` on 5 platform packages, no os/cpu) + 5 platform packages `@minecraft-mcp-rs/minecraft-mcp-rs-{windows-x64,windows-arm64,darwin-arm64,linux-x64,linux-arm64}` (scoped under the npm org; os/cpu fields; binaries staged by CI, `.gitignore`d locally; directory names stay unscoped, the scoping lives in each package.json's `name`). `npm/scripts/sync-versions.mjs` stamps the Cargo.toml version into every package.json and the main package's optionalDependencies (run it after bumping Cargo). `.github/workflows/release.yml`'s `npm-publish` job publishes platform-first then main with `--provenance` (which requires `id-token: write` + GitHub-hosted runner), skips already-published versions, and authenticates via npm Trusted Publishing (OIDC — each package on npmjs.com → Settings → Trusted Publishers → GitHub Actions, owner `halfoffive`, workflow `release.yml`) OR the `NPM_TOKEN` secret (granular token, NEVER commit it; used via `NODE_AUTH_TOKEN` when present).
